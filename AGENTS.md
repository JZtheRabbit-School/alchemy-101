# Working agreement

## Help and clarification
- When a request is unclear, help the user choose the kind of help they need (for example: explanation, design discussion, debugging, or implementation), or ask focused clarification questions.
- Use established decisions in JOURNAL.md before asking questions already answered.
- State reasonable assumptions explicitly. Do not silently decide consequential gameplay or design changes.

## Small, inspectable changes
- Work in small steps the user can inspect and test.
- Explain what changed, why, and how the user can check it.
- Distinguish verified behavior, planned behavior, assumptions, and untested work. Never claim a check passed unless it was run.
- Keep unrelated changes out of the current task.

## Documentation and continuity
- README.md is the player instruction manual. Label unimplemented behavior as planned; avoid exposing secret recipes, hidden achievement thresholds, or endings there.
- JOURNAL.md records dated discussions, decisions, changes, validation, assumptions, and remaining questions. Preserve history and note superseded decisions rather than silently rewriting them.
- Use America/New_York dates. If a historical date cannot be established from the conversation, mark it uncertain.
- Before ending each working session, ask: "What part of the game or today's changes do you still feel you cannot explain?"
- Whenever project files change, remind the user about committing and pushing to GitHub. If they already authorized a push for the current work, complete it and report the result instead of asking again.
- Never claim local changes are on GitHub before verifying the remote result.

## Project intent
- Preserve player choice, experimentation, surprise, and deliberately absurd combinations.
- Do not reveal a final objective in the basement or add reassuring promises about drinking.
- Use the latest confirmed gameplay and visual decisions in JOURNAL.md.
